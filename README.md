# Цифровий портал співробітника — MVP (Streamlit)

Робочий прототип двох модулів з ТЗ:

1. **Єдине цифрове вікно співробітника** — розклад змін, заявки на довідки,
   заяви на відпустку/відгул з електронним підбором погоджувача, таргетовані
   сповіщення, проходження інструктажів з ОП та квартальне тестування.
2. **Інтелектуальна база технічних знань** — гібридний пошук (TF-IDF +
   косинусна схожість як заглушка RAG/векторного пошуку) по регламентах,
   паспортах обладнання, схемах та НПАОП, з розмежуванням доступу за рівнем
   допуску.
3. **Енергетична та диспетчерська специфіка** (для обленерго/енергокомпаній):
   - *Журнал оперативних розпоряджень / аварійних заяв* — фіксація диспетчером
     аварійних відключень, спрацювань захисту та виїздів оперативно-виїзних
     бригад (ОВБ), зі статусами «Відкрито → В роботі → Закрито».
   - *Карта підстанцій* (`st.pydeck_chart`) — геодані об'єктів мережі з
     кольоровим індикатором статусу (в роботі / планове відключення / аварія)
     та прив'язаними до кожної підстанції паспортами, схемами й інструкціями
     з бази знань.
4. **Розширення для співробітників та HR**:
   - *Інтерактивний календар змін* (`streamlit-calendar`, FullCalendar) —
     повноцінний місячний віджет замість таблиці табеля, з кольоровим
     кодуванням типу зміни.
   - *Заявки на обладнання / ЗІЗ* — електромонтер замовляє спецодяг чи
     інструмент або повідомляє про несправність обладнання (з позначкою
     «Термінова» для критичних випадків); HR/адміністратор обробляє заявки
     у своїй панелі.
   - *Модуль адаптації (Onboarding)* — персональний послідовний ланцюжок
     завдань для новачка: пройти вступний інструктаж (авто-зарахування за
     результатом тесту), ознайомитися з регламентами підрозділу, познайомитися
     з ментором. Кожен наступний крок розблоковується лише після виконання
     попереднього.

## Запуск

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

При першому запуску автоматично створюється `portal.db` (SQLite) і
наповнюється демо-даними (`seed_data.py`).

## Структура проєкту

```
hr_portal/
├── app.py            # Streamlit UI та маршрутизація сторінок
├── db.py              # Схема SQLite та підключення
├── seed_data.py        # Демо-дані (користувачі, документи, підстанції, події)
├── kb_search.py        # Гібридний пошук по базі знань
└── requirements.txt
```

> Якщо оновлюєте вже запущений проєкт — видаліть старий `portal.db` перед
> першим запуском нової версії, бо змінилась схема БД (додано таблиці
> `substations`, `operational_log`, `equipment_requests`, `onboarding_tasks`,
> колонку `kb_documents.substation_id`, колонки `users.hire_date` та
> `users.is_new_hire`). Демо-дані пересіються автоматично.

## Що спрощено відносно повного ТЗ (і як довести до прод-рівня)

| У ТЗ | У цьому MVP | Для прод-версії |
|---|---|---|
| SSO через Active Directory/LDAP | Логін/пароль у SQLite | Підключити `python-ldap` / SAML / OIDC-провайдер |
| Векторна БД (Qdrant/Milvus/pgvector) + локальна LLM (Llama/Mistral) | TF-IDF + косинусна схожість (scikit-learn) | Замінити `kb_search.py` на ембединги + виклик LLM через Ollama/vLLM |
| Синхронізація з ERP/HR (BAS/1С, SAP) | Ручні демо-дані | Нічний ETL або REST-інтеграція в `db.py` |
| S3-сумісне сховище для PDF/креслень | Текст документа в SQLite | Зберігати файл у S3, у БД — лише метадані та індекс |
| Реальні сповіщення (push/email) | Стрічка в інтерфейсі | Інтеграція з email/SMS/push-шлюзом |
| Карта з тайлами (OSM/Google Maps) | `pydeck` без тайлового провайдера (потрібен API-ключ Mapbox/Carto) | Додати `mapbox_key` у `pdk.Deck` або перейти на `streamlit-folium` |
| SCADA/АСДУ (реальний статус обладнання) | Статус підстанції вручну оновлюється диспетчером через журнал подій | Інтеграція з АСДУ/SCADA для автоматичного оновлення статусів |
| Складський облік ЗІЗ/інструменту | Заявка — це запис у БД, без перевірки залишків на складі | Інтеграція зі складською системою (WMS) для перевірки наявності |
| Призначення ментора та плану адаптації | Ланцюжок завдань створюється вручну в `seed_data.py` | HR створює план адаптації через форму при оформленні нового співробітника в ERP/HR-системі |

Загальна архітектура (модулі, ролі доступу, категорії документів) відповідає
розділам 1–3 технічного завдання; етапність реалізації описана в розділі 4.
