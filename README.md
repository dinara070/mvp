# Цифровий портал співробітника — MVP (Streamlit)

Робочий прототип двох модулів з ТЗ:

1. **Єдине цифрове вікно співробітника** — розклад змін, заявки на довідки,
   заяви на відпустку/відгул з електронним підбором погоджувача, таргетовані
   сповіщення, проходження інструктажів з ОП та квартальне тестування.
2. **Інтелектуальна база технічних знань** — гібридний пошук (TF-IDF +
   косинусна схожість як заглушка RAG/векторного пошуку) по регламентах,
   паспортах обладнання, схемах та НПАОП, з розмежуванням доступу за рівнем
   допуску.
3. **Енергетична та диспетчерська специфіка** (для обленерго/енергокомпаній):
   - *Журнал оперативних розпоряджень / аварійних заяв* — фіксація диспетчером
     аварійних відключень, спрацювань захисту та виїздів оперативно-виїзних
     бригад (ОВБ), зі статусами «Відкрито → В роботі → Закрито».
   - *Карта підстанцій* (`st.pydeck_chart`) — геодані об'єктів мережі з
     кольоровим індикатором статусу (в роботі / планове відключення / аварія)
     та прив'язаними до кожної підстанції паспортами, схемами й інструкціями
     з бази знань.
4. **Розширення для співробітників та HR**:
   - *Інтерактивний календар змін* (`streamlit-calendar`, FullCalendar) —
     повноцінний місячний віджет замість таблиці табеля, з кольоровим
     кодуванням типу зміни.
   - *Заявки на обладнання / ЗІЗ* — електромонтер замовляє спецодяг чи
     інструмент або повідомляє про несправність обладнання (з позначкою
     «Термінова» для критичних випадків); HR/адміністратор обробляє заявки
     у своїй панелі.
   - *Модуль адаптації (Onboarding)* — персональний послідовний ланцюжок
     завдань для новачка: пройти вступний інструктаж (авто-зарахування за
     результатом тесту), ознайомитися з регламентами підрозділу, познайомитися
     з ментором. Кожен наступний крок розблоковується лише після виконання
     попереднього.
5. **🛠️ Розширена роль Адміністратора («Управління системою»)** — окрема
   панель, доступна лише ролі `admin`, яка закриває функціональні прогалини
   й дає повний огляд/контроль над усім, що бачать інші ролі:
   - *Огляд* — зведений дашборд: кількість співробітників, відкритих заяв
     на відпустку/довідки/ЗІЗ, незакритих оперативних подій, документів у
     базі знань, підстанцій, новачків в адаптації, та стрічка активних
     аварійних подій.
   - *Користувачі* — повний CRUD: створення нового співробітника (логін,
     тимчасовий пароль, посада, підрозділ, філія, роль, рівень допуску,
     позначка «новачок»), редагування ролі/рівня допуску/підрозділу будь-кого
     та скидання пароля.
   - *Розклади* — перегляд і редагування календаря змін **будь-якого**
     співробітника (не лише свого власного, як у звичайного працівника).
   - *База знань* — повний CRUD документів (регламенти, схеми, паспорти,
     НПАОП): створення, редагування змісту/категорії/рівня допуску/прив'язки
     до підстанції.
   - *Підстанції* — додавання нових об'єктів мережі та ручна зміна статусу
     (в роботі / планове відключення / аварія) для карти.
   - *Адаптація новачків* — огляд прогресу всіх активних планів адаптації та
     конструктор кроків для будь-якого співробітника (автоматично позначає
     користувача новачком).

   Крім цієї окремої панелі, `admin` також бачить усі розділи, доступні
   іншим ролям (кабінет співробітника, база знань, журнал оперативних подій,
   карта підстанцій, HR-панель, адміністрування ОП) — тобто має повну
   видимість системи з одного акаунта.
6. **🤖 Штучний інтелект та RAG**:
   - *Чат-асистент технічної підтримки* (`🤖 Чат-асистент (RAG)`, доступний
     усім ролям) — RAG-пайплайн: пошук релевантних документів бази знань
     активним бекендом (`vector_store.py`) → побудова контексту → генерація
     відповіді LLM (OpenAI API або локальна Ollama через `llm_client.py`) з
     обов'язковим посиланням на джерела. Якщо LLM не налаштована — асистент
     не мовчить, а чесно повертає найрелевантніші фрагменти з бази знань без
     узагальнення (fallback-режим). Історія чату зберігається в
     `chat_history`, кожен запит логується в аудит.
   - *Автогенерація тестів з ОП* (`quiz_generator.py`) — інженер з ОП або
     адміністратор завантажує PDF (`pdf_reader.py` витягує текст) або
     вставляє текст регламенту вручну, вказує кількість питань — LLM
     генерує тестові питання з варіантами відповіді у форматі JSON.
     Без LLM спрацьовує детерміністичний евристичний fallback
     («заповни пропуск» на основі найінформативніших речень документа).
     Згенеровані питання можна відредагувати перед збереженням; збереження
     створює новий запис у `safety_instructions` + `quiz_questions`, одразу
     доступний у розділі «Інструктажі та ОП». Доступно і в панелі
     «Адміністрування ОП» (safety_admin), і в «🛠️ Управління системою» (admin).
7. **🏗️ Production-ready інфраструктура** (пункт 2 з ТЗ):
   - *Векторний пошук* — `vector_store.py`: TF-IDF за замовчуванням АБО
     справжній Qdrant (реальний робочий клієнт `qdrant-client` + ембединги
     через OpenAI-сумісний API), перемикається змінною `VECTOR_BACKEND=qdrant`.
     Fail-safe: будь-яка помилка з'єднання з Qdrant прозоро повертає TF-IDF,
     щоб пошук ніколи не ламався.
   - *SSO / Active Directory* — `auth.py`: реальний BIND-запит до домену
     через `ldap3` (NTLM), активується змінною `LDAP_SERVER`. Профіль
     співробітника (роль, рівень допуску, підрозділ) після BIND береться з
     локальної таблиці `users`, яку в проді синхронізує ERP/HR-інтеграція.
   - *PostgreSQL + pgvector* — `postgres_schema.sql`: повна референсна схема
     для міграції з SQLite (SERIAL, TIMESTAMPTZ, нативний `VECTOR(1536)` для
     ембедингів, індекс `ivfflat`). Це довідкова ціль міграції, а не другий
     паралельний робочий бекенд застосунку — див. пояснення в коментарях
     файлу й у таблиці нижче.
   - *Audit Trail* — `audit.py` + таблиця `audit_log`: хто, коли й що зробив
     — логін, перегляд документа (зокрема з обмеженим рівнем допуску),
     складання тесту, зміна статусу будь-якої заявки, створення/зміна/
     видалення документів бази знань, запити до AI-асистента, генерація
     тестів AI. Перегляд і фільтрація — у «🛠️ Управління системою → 🕵️ Аудит».

   Усі AI/production-інтеграції налаштовуються через `.env` (див.
   `.env.example`) і мають безпечний fallback — застосунок повністю
   функціональний і без жодної з них.

## Запуск

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
streamlit run app.py
```

При першому запуску автоматично створюється `portal.db` (SQLite) і
наповнюється демо-даними (`seed_data.py`).

### Підключення AI та production-інтеграцій (опційно)

```bash
cp .env.example .env
# відредагуйте .env: OPENAI_API_KEY (або локальна Ollama), VECTOR_BACKEND,
# LDAP_SERVER тощо
pip install -r requirements-optional.txt   # ldap3, qdrant-client, psycopg2-binary
```

Без цього кроку застосунок повністю працює у демо-режимі: локальний логін,
TF-IDF пошук, AI-функції у fallback-режимі (без LLM).

## Структура проєкту

```
hr_portal/
├── app.py                    # Streamlit UI та маршрутизація сторінок
├── db.py                      # Схема SQLite та підключення
├── seed_data.py                # Демо-дані (користувачі, документи, підстанції, події)
├── kb_search.py                # TF-IDF реалізація гібридного пошуку
├── vector_store.py              # Абстракція пошуку: TF-IDF / Qdrant
├── llm_client.py                # Клієнт LLM (OpenAI API / Ollama) з fallback
├── rag_chat.py                  # RAG-пайплайн чат-асистента
├── quiz_generator.py            # Автогенерація тестів з ОП (LLM / евристика)
├── pdf_reader.py                 # Витяг тексту з PDF
├── auth.py                       # Автентифікація: демо (SQLite) / LDAP-AD
├── audit.py                      # Журнал аудиту дій (Audit Trail)
├── postgres_schema.sql            # Референсна схема для міграції на PostgreSQL+pgvector
├── .env.example                   # Приклад конфігурації AI/production-інтеграцій
├── requirements.txt                # Базові залежності (працює "з коробки")
└── requirements-optional.txt        # ldap3, qdrant-client, psycopg2-binary
```

> Якщо оновлюєте вже запущений проєкт — видаліть старий `portal.db` перед
> першим запуском нової версії, бо змінилась схема БД (додано таблиці
> `substations`, `operational_log`, `equipment_requests`, `onboarding_tasks`,
> `audit_log`, `chat_history`, колонку `kb_documents.substation_id`, колонки
> `users.hire_date` та `users.is_new_hire`). Демо-дані пересіються автоматично.

## Що спрощено відносно повного ТЗ (і як довести до прод-рівня)

| У ТЗ | У цьому MVP | Для прод-версії |
|---|---|---|
| SSO через Active Directory/LDAP | ✅ Реалізовано (`auth.py`, `ldap3`, вимикається за замовч.) | Додати SAML/OIDC як альтернативу прямому BIND, кешування груп AD |
| Векторна БД (Qdrant/pgvector) + локальна LLM | ✅ Реалізовано: Qdrant-бекенд (`vector_store.py`) + OpenAI/Ollama-клієнт (`llm_client.py`), TF-IDF — бекенд за замовчуванням | Фонова (а не "на льоту") індексація документів при їх збереженні в адмінці |
| RAG чат-асистент | ✅ Реалізовано (`rag_chat.py`), з fallback без LLM | Стрімінг відповіді, per-message фідбек (👍/👎) для донавчання |
| Автогенерація тестів з ОП з PDF | ✅ Реалізовано (`quiz_generator.py` + `pdf_reader.py`), з евристичним fallback без LLM | OCR для сканованих PDF без текстового шару; перевірка якості дистракторів людиною перед публікацією (зараз це вже передбачено — питання редагуються перед збереженням) |
| Audit Trail (журнал аудиту дій) | ✅ Реалізовано (`audit.py`, таблиця `audit_log`, вкладка «🕵️ Аудит») | На рівні прав БД заборонити UPDATE/DELETE над `audit_log` (справжній append-only) |
| PostgreSQL замість SQLite | 📄 Довідкова схема (`postgres_schema.sql`), НЕ підключена як другий робочий бекенд | Точковий рефакторинг `db.py`/`app.py` під психопг2 (плейсхолдери `?`→`%s`, `lastrowid`→`RETURNING id`) — обсяг таблиця за таблицею, без зупинки роботи застосунку |
| Синхронізація з ERP/HR (BAS/1С, SAP) | Ручні демо-дані | Нічний ETL або REST-інтеграція в `db.py` |
| S3-сумісне сховище для PDF/креслень | Текст документа в SQLite | Зберігати файл у S3, у БД — лише метадані та індекс |
| Реальні сповіщення (push/email) | Стрічка в інтерфейсі | Інтеграція з email/SMS/push-шлюзом |
| Карта з тайлами (OSM/Google Maps) | `pydeck` без тайлового провайдера (потрібен API-ключ Mapbox/Carto) | Додати `mapbox_key` у `pdk.Deck` або перейти на `streamlit-folium` |
| SCADA/АСДУ (реальний статус обладнання) | Статус підстанції вручну оновлюється диспетчером через журнал подій | Інтеграція з АСДУ/SCADA для автоматичного оновлення статусів |
| Складський облік ЗІЗ/інструменту | Заявка — це запис у БД, без перевірки залишків на складі | Інтеграція зі складською системою (WMS) для перевірки наявності |

Загальна архітектура (модулі, ролі доступу, категорії документів) відповідає
розділам 1–3 технічного завдання; етапність реалізації описана в розділі 4.

### Чесно про межі "production-ready" у цій версії

Пункти з ✅ вище — це реальний, синтаксично коректний, протестований (де це
можливо офлайн) код інтеграцій, а не заглушки, і вони автоматично активуються
відповідними змінними в `.env`. Але:
- **Qdrant і LDAP** не були протестовані проти справжнього сервера Qdrant чи
  контролера домену в цьому середовищі (немає мережевого доступу до таких
  сервісів у пісочниці розробки) — перевірте підключення у своєму оточенні
  перед продакшн-використанням.
- **OpenAI/Ollama клієнт** протестовано на рівні коректності виклику API та
  fallback-логіки (коли ключа немає) — з реальним ключем варто перевірити
  ліміти токенів/швидкості для вашого обсягу документів.
- **PostgreSQL** свідомо залишено як довідкова схема, а не другий паралельний
  бекенд — часткова, невідтестована заміна СУБД в проді небезпечніша, ніж
  чесно позначений scope.
